4. COMPLETE PRESENT STATUS INVESTIGATION
----------------------------------------
4.1 Normal punch-in

File: src/attendance/attendance.service.ts
Method: clockInWithClient()

The method creates AttendanceRecord with:

  status: isLate ? LATE : PRESENT

Requirements:

  - user ID is required.
  - clockIn is always populated.
  - clockOut is not required.
  - zero-hour PRESENT is not created by this current path.
  - a newly opened record is immediately PRESENT or LATE.

4.2 Normal punch-out

Method: clockOutWithClient()

Status calculation:

  less than 4 hours: ABSENT
  4 hours to less than 7 hours: HALF_DAY
  7 hours or more: PRESENT

The status is calculated from server-side elapsed time.

4.3 Approved regularization

Method: processRegularization()

An approved regularization updates AttendanceRecord with HALF_DAY, LATE, or
PRESENT. Its lower threshold uses AttendancePolicy.halfDayHours, while normal
checkout uses hardcoded 4/7 hour thresholds. Equivalent hours can therefore be
classified differently in the two paths.

4.4 Prisma defaults

Both Attendance and AttendanceRecord default status to PRESENT. Omitting status
from a direct create can therefore produce PRESENT without validated punches.

4.5 Legacy punch-out fallback

The legacy fallback can create an Attendance row when no row exists:

  punchIn: punchOut
  punchOut: punchOut
  totalHours: 0

Status is omitted and Prisma applies PRESENT. This creates a zero-hour PRESENT
row, although punchIn is populated in this exact path.

4.6 Seed/import

prisma/add-august-attendance.ts creates valid AttendanceRecord rows with
clock-in, clock-out, and totalHours of 9. It does not explain the reported
null/null/zero/PRESENT display.

6. PUNCH-IN FLOW
----------------
Newer frontend flow:

  Attendance.tsx
    -> useAttendance.punchIn()
    -> ApiService.punchIn()
    -> POST /api/attendance/punch-in
    -> AttendanceController.punchIn()
    -> requireSelfEmployeeId()
    -> AttendanceService.punchIn()
    -> requireActiveEmployee()
    -> getLocationStatus()
    -> Prisma transaction
    -> AttendanceRecord + AttendanceLog

Newer punch-in behavior:

  - employee ID is derived from request.user.employeeId.
  - the client cannot select another employee.
  - active employee status is checked.
  - duplicate punch-in is checked.
  - date is normalized to the server business date.
  - WFH and office location are evaluated.
  - AttendanceRecord and AttendanceLog are written in a transaction.

Legacy flow:

  POST /api/attendance/clock-in
    -> request.user.id
    -> AttendanceService.clockIn()
    -> AttendanceRecord

The legacy route bypasses the newer employee ID resolution, active employee
check, geolocation handling, and explicit AttendanceLog creation.

7. PUNCH-OUT FLOW
-----------------
Newer frontend flow:

  Attendance.tsx
    -> PunchInOutModal
    -> useAttendance.punchOut()
    -> ApiService.punchOut()
    -> POST /api/attendance/punch-out
    -> requireSelfEmployeeId()
    -> AttendanceService.punchOut()
    -> Prisma transaction
    -> AttendanceRecord update + OUT log

Implemented behavior:

  - server timestamp is authoritative.
  - totalHours is calculated from stored clockIn and server checkout time.
  - repeated checkout is rejected when clockOut already exists.
  - status follows the 4/7 hour thresholds.

Legacy route:

  POST /api/attendance/clock-out

This route accepts an optional client-supplied date and can modify a historical
business date. It does not use the same stronger flow as punch-out.

9. VIRTUAL ATTENDANCE LOGIC
---------------------------
getAttendanceHistory() generates virtual rows dynamically.

Behavior:

  - persisted AttendanceRecord rows are loaded first;
  - eligible dates come from WorkingDaysService;
  - missing eligible dates become virtual ABSENT rows;
  - approved leave dates become virtual LEAVE rows;
  - existing attendance rows are not replaced by virtual ABSENT;
  - virtual logic never generates PRESENT;
  - future dates are excluded from current-month history;
  - future months return no history rows.

10. WORKING-DAY LOGIC
---------------------
WorkingDaysService.getWorkingDates():

  - Sunday is excluded.
  - Normal Saturday is excluded.
  - Sales Saturday is included.
  - Monday-Friday are included.
  - Holidays are excluded.

The service is used by attendance, dashboard, reports, payroll, and WFH
location checks.

Holiday location is not considered by HolidaysService.isHoliday(). A populated
location-specific holiday can therefore exclude all employees from working-day
calculations.

11. LEAVE INTEGRATION
---------------------
Approved leave:

  - becomes virtual LEAVE in attendance history;
  - contributes to summary leaveDays;
  - is excluded from summary attendance classification;
  - does not consistently update the persisted AttendanceRecord.

Pending, rejected, and cancelled leave are not selected by the approved-leave
queries and therefore become ABSENT when the date is an eligible working day.

Actual attendance on an approved leave date is overridden at read time by the
leave projection.

12. HOLIDAY INTEGRATION
-----------------------
  - holidays are excluded from working-day denominators;
  - punches are still accepted on holidays;
  - holiday location is ignored by isHoliday();
  - holiday logic does not directly create PRESENT;
  - holiday logic can prevent virtual ABSENT generation.

13. WFH INTEGRATION
-------------------
Approved WFH affects locationStatus only.

  - WFH does not directly change PRESENT, ABSENT, or HALF_DAY.
  - approved WFH is checked by date overlap.
  - office distance determines OFFICE or OUTSIDE when WFH does not apply.
  - WFH does not create attendance rows.

14. MONTH/YEAR LOGIC
--------------------
EmployeeAttendance.tsx correctly maintains selectedMonth as YYYY-MM and sends:

  - numeric month/year to Details;
  - YYYY-MM to Summary.

The self Attendance page has a confirmed frontend defect:

  Attendance.tsx calls useAttendance(selectedMonth)

but useAttendance() expects an options object containing month and year.

As a result, the selected month is ignored by the hook and the hook falls back
to the current month/year.

Historical backend AttendanceRecord queries generally use a
[monthStart, nextMonthStart) range. Current month calculations are capped at
the current day. Reports, dashboard, and payroll implement their own date
ranges, creating boundary inconsistency risk.

15. SUMMARY VS DETAILS
----------------------
Details:

  EmployeeAttendance.tsx
    -> getEmployeeAttendance()
    -> GET /attendance/employee/:id/monthly
    -> getMyAttendanceForEmployee()
    -> getAttendanceHistory()
    -> AttendanceRecord plus virtual rows

Summary:

  EmployeeAttendance.tsx
    -> getEmployeeAttendanceSummary()
    -> GET /attendance/employee/:id/summary
    -> getEmployeeMonthlySummary()
    -> AttendanceRecord + Leave + WorkingDaysService

Both use the selected Employee.id and resolve attendance through the employee's
User.id. They use the same selected month in EmployeeAttendance.

They differ because Details projects virtual rows while Summary calculates
counts independently. Leave precedence and date handling are duplicated.

The current system can produce Details/Summary disagreement when:

  - approved leave overlaps an attendance record;
  - LATE is not represented consistently in frontend types;
  - date serialization crosses a timezone boundary;
  - stale or different deployment data is used;
  - the self Attendance month-selection bug is involved.

18. DASHBOARD, REPORTS, AND PAYROLL
-----------------------------------
Dashboard:

  - reads AttendanceRecord;
  - counts PRESENT and LATE as one day;
  - counts HALF_DAY as 0.5;
  - uses WorkingDaysService;
  - calculates approved leave separately.

Reports:

  - read AttendanceRecord;
  - count PRESENT and LATE as present;
  - count HALF_DAY and ABSENT independently;
  - use separate monthly range and leave calculations.

Payroll:

  - reads AttendanceRecord;
  - counts PRESENT and LATE as present;
  - counts HALF_DAY as 0.5;
  - adds approved leave to payable days;
  - trusts stored status without validating punches.

A malformed PRESENT row can therefore affect payroll, reports, dashboard values,
and exports.
