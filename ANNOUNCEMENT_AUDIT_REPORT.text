================================

Date: 2026-09-10
Scope: Audit only. No code changes, no refactor, no migrations, no implementation.

1. Current Announcement architecture--
-----------------------------------

Backend module:
- src/modules/announcement/announcement.module.ts
- src/modules/announcement/announcement.controller.ts
- src/modules/announcement/announcement.service.ts
- src/modules/announcement/dto/create-announcement.dto.ts
- src/modules/announcement/dto/update-announcement.dto.ts
- src/modules/announcement/announcement.service.spec.ts

Authentication and guard flow:
- Controller is guarded by JwtAuthGuard and RolesGuard: src/auth/guards/jwt-auth.guard.ts and src/common/guards/roles.guard.ts.
- JwtStrategy returns request.user with: id, role, employeeId, email. See src/auth/strategies/jwt.strategy.ts.
- The current announcement implementation uses request.user fields, but does not use team manager relationships from Team.managerId and Employee.teamId for visibility.

Architecture summary:
- Announcement is a lightweight module with controller + service only.
- List/read logic is filtered in the announcement service based on ALL vs DEPARTMENT visibility.
- Mutations are guarded with RolesGuard role decorators, but there is no announcement-specific ownership or visibility enforcement.
- There is no announcement detail route by ID.
- There is no team-scoped announcement policy.
- There is no role-specific or employee-specific audience model in the current implementation.

2. Current backend endpoints
----------------------------

Controller: src/modules/announcement/announcement.controller.ts

POST /announcements
- Auth: JWT required
- Role requirement: RolesGuard with MANAGEMENT_ROLES = ['SUPER_ADMIN', 'Super_admin', 'CEO', 'HR', 'HR_MANAGER', 'MANAGER', 'IT_MANAGER', 'SALES_MANAGER']
- Logic: createAnnouncement(dto, req.user)
- Data returned: Prisma announcement create result
- Server-side visibility filtering: No
- Ownership check: No
- Team scope check: No
- Client-supplied IDs: Not used in announcement authorization. The service derives audience from role and employee department.

GET /announcements
- Auth: JWT required
- Role requirement: None explicitly
- Logic: getAnnouncements(req.user)
- Data returned: list of announcements matching the current user's visibility
- Server-side filtering: Yes
- Ownership check: No
- Team scope check: No
- Client-supplied IDs: No

GET /announcements/feed
- Auth: JWT required
- Role requirement: None explicitly
- Logic: alias of getAnnouncements
- Data returned: same as list
- Server-side filtering: Yes
- Ownership check: No
- Team scope check: No
- Client-supplied IDs: No

PATCH /announcements/:id
- Auth: JWT required
- Role requirement: MANAGEMENT_ROLES
- Logic: updateAnnouncement(id, dto)
- Data returned: Prisma update result
- Server-side visibility filtering: No
- Ownership check: No
- Team scope check: No
- Client-supplied IDs: No direct authorization from payload; updates by id only

DELETE /announcements/:id
- Auth: JWT required
- Role requirement: MANAGEMENT_ROLES
- Logic: deleteAnnouncement(id)
- Data returned: Prisma delete result or NotFoundException
- Server-side visibility filtering: No
- Ownership check: No
- Team scope check: No
- Client-supplied IDs: No

POST /announcements/:id/read
- Auth: JWT required
- Role requirement: None explicitly
- Logic: markAsRead(id, req.user.employeeId)
- Data returned: createMany on announcementReads
- Server-side visibility filtering: No
- Ownership check: No
- Team scope check: No
- Client-supplied IDs: Uses authenticated employeeId from JWT, but does not validate the announcement is visible to that employee.

Important note: There is no GET /announcements/:id detail route.

- Route is present in App.tsx without any role allowlist: path="announcements" element={<ProtectedRoute><AnnouncementsPage /></ProtectedRoute>}.
- So the frontend does not restrict the module by role at route level.

Create/Edit/Delete UI:
- The page computes canManage using:
  - MANAGEMENT_ROLES = ['SUPER_ADMIN', 'CEO', 'HR']
  - MANAGER_ROLES = ['IT_MANAGER', 'SALES_MANAGER', 'FINANCE_MANAGER']
- In practice, the page allows create/edit/delete based on a broader condition:
  - user.role in MANAGEMENT_ROLES or MANAGER_ROLES
- Therefore FINANCE_MANAGER is currently treated as a management role on the frontend and sees create/edit/delete controls.

API usage:
- The page expects methods like getAnnouncements(), createAnnouncement(), updateAnnouncement(), deleteAnnouncement(), markAnnouncementAsRead().
- In the inspected frontend API service, these concrete announcement methods are not implemented in the same file as other API helpers; the page still invokes them as if they exist, which indicates a mismatch between page expectations and actual service implementation.

Response format expectations:
- FetchAnnouncements does: setAnnouncements(Array.isArray(data) ? data : []);
- So the frontend expects a raw array response and not a wrapped envelope.

Local filtering:
- Filter states: all, pinned, unread, department.
- Announcements are filtered locally on the page after fetching.
- This is only UI filtering; it does not replace server-side authorization.

Team/employee/role sending:
- Frontend does not appear to send teamId, employeeId, or role as authorization inputs to the announcement API.
- The UI does use user.role and department from auth state to decide UI behavior and audience defaults, but not as trusted server-side authorization input.

Unauthorized direct API calls:
- A user could still call announcement routes directly if authenticated, because there is no explicit role enforcement on the read list and mark-read endpoints in the controller.
- The frontend route/module does not protect the feature by role, so unauthorised users can still access the page UI in the client.

5. Current authorization behavior
---------------------------------

Create logic in AnnouncementService:
- Resolves employee by reqUser.employeeId
- Gets departmentId from reqUser.departmentId or employee.department
- Uses global roles set: ['SUPER_ADMIN', 'CEO', 'HR', 'HR_MANAGER']
- If role is global => targetAudience = ALL, departmentId = null
- Else => targetAudience = DEPARTMENT, departmentId = departmentId string
- createdById = reqUser.id

List logic in AnnouncementService:
- Finds active announcements where expiresAt is null or gte current time
- If departmentId is null => only ALL
- Else => OR of ALL and DEPARTMENT with same departmentId
- Includes reads for current employeeId

Update logic:
- AnnouncementService.updateAnnouncement(id, dto)
- No ownership check
- No authorization against current user role
- No visibility check

Delete logic:
- AnnouncementService.deleteAnnouncement(id)
- No ownership check
- No authorization against current user role
- No visibility check

Mark as read:
- Requires employeeId
- Checks only that announcement exists
- Does not check whether employee is authorized to read the announcement

This means current announcement logic is role/baseline gated at controller entry for some operations, but not sufficiently protected in service logic.

6. Current visibility/audience logic
------------------------------------

Current logic currently decides:
- Who can create?
  - Controller route allows MANAGEMENT_ROLES, but service itself does not enforce role. It simply uses reqUser.role to determine audience.
- Who can edit?
  - Any user who passes RolesGuard and calls PATCH /announcements/:id can update any record.
- Who can delete?
  - Any user who passes RolesGuard and calls DELETE /announcements/:id can delete any record.
- Who can see all announcements?
  - There is no dedicated all-visibility role check beyond list logic that includes ALL announcements when departmentId is null or when global role is effectively the only route to set ALL.
- Who can see team announcements?
  - No current team announcement concept exists.
- How is announcement audience represented?
  - Only as ALL or DEPARTMENT, not manager/team role/employee-specific.
- Current feature capabilities actually present:
  - global announcement = yes
  - team announcement = no
  - employee-specific announcement = no
  - role-specific announcement = no
  - author-only visibility = no
  - publish status = no
  - expiration = yes (expiresAt)
  - active/inactive = no (not represented as status field)
  - read/unread state = yes (AnnouncementRead relation + includes reads in query)

9. Exact gaps between current and target behavior
--------------------------------------------------

1. Current implementation uses department/global visibility; target requires org-wide + team-scoped + manager-scoped visibility.
2. Current backend does not enforce authorization on update/delete by ownership or by manager/role rules.
3. Current backend does not enforce visibility on direct announcement ID access.
4. Current backend does not restrict manager access to their own team only.
5. Current backend does not distinguish Sales/IT/Finance manager-only visibility.
6. Current frontend allows the announcement module to all authenticated users and shows create/edit/delete to FINANCE_MANAGER, even though backend denies that access.
7. Current Prisma model cannot express team-only, role-only, or manager-only announcement audiences without a schema change.
8. Current service ignores DTO targetAudience and always derives audience from user role and department.
9. There is no detail endpoint enforcing list/detail visibility.
10. Current mark-as-read endpoint allows unauthorized read access to any announcement id if the user can authenticate.

11. Schema change required: YES
-------------------------------

Yes. The database schema is insufficient to implement the approved business behavior.

Minimum schema changes required:
- Add an announcement audience or team-target field that can represent Sales team, IT team, or global audience.
- Add explicit team assignment support if managers must target their team.
- Preserve createdById as the author pointer, but enforce it in update/delete authorization.
- Ensure the schema can support organization-wide + team-scoped + role-scoped visibility rules.

Current schema cannot represent required behavior because:
- AnnouncementAudience only supports ALL and DEPARTMENT.
- There is no Team relation on Announcement.
- There is no role-target or manager-target concept.
- There is no explicit team-only audience field.
- There is no visibility/ownership enforcement model beyond createdById.

Final conclusion
----------------

The current Announcement module is a simple ALL vs DEPARTMENT feed with no team-aware, role-aware, or owner-aware authorization model. The target business requirement is substantially stricter and requires both schema and service/controller changes. The backend is the source of truth and must be corrected before any frontend behavior can be trusted.
