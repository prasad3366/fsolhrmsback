================================

Scope
-----
Read-only audit of the existing Holiday visibility issue. No application code,
Prisma schema, or migrations were modified during this audit.

A. EXACT ROOT CAUSE
-------------------
The Holiday page submits an empty Location as the string "".

The backend stores that value unchanged. Employee holiday visibility treats
only NULL as a global holiday:

  holiday.location === null || normalizedHolidayLocation === employeeLocation

Therefore:

  location = NULL  -> global holiday
  location = ""    -> treated as location-specific
  location = "Pune" -> visible only to matching employee city

Employees whose Employee.city is a normal populated city do not match the
empty string, so a holiday that HR intended to be global is hidden from them.

C. DATABASE STORAGE RESULT
--------------------------
The frontend sends "" and the backend passes it directly to Prisma:

  location: data.location

Consequently, PostgreSQL stores an empty string as "", not NULL.

If the location property is omitted completely, Prisma stores NULL.

A read-only query against the configured local database returned current rows
with empty-string locations:

  id  name             location
  --  ---------------  --------
  2   Mani Birthday    ""
  1   Ganesh Birthday  ""

The configured database is the local PostgreSQL database from .env. Production
must be checked separately if it uses a different database connection.

D. CURRENT BEHAVIOR VS EXPECTED BEHAVIOR
----------------------------------------
Stored value       Current behavior                 Expected behavior
-----------------  --------------------------------  --------------------------
NULL               Visible to all employees         Global
""                 Usually hidden from employees   Global
"   "              Usually hidden from employees   Global
"Pune"             Visible to Pune employees        Location-specific

Case and surrounding whitespace are normalized correctly for populated
locations. Blank values are not converted to NULL or otherwise recognized as
global.

An employee with Employee.city = NULL also does not match a holiday whose
location is "".

E. MANAGEMENT VS EMPLOYEE LISTING
---------------------------------
Management users use:

  GET /holidays?year=YYYY

The management query filters only by year and returns all holidays.

Employees use:

  GET /holidays/my

The employee endpoint applies the location filter. This explains why HR can
see the holiday while some employees cannot.

F. OTHER HOLIDAY CONSUMERS
--------------------------
WorkingDaysService calls HolidaysService.isHoliday(date).

isHoliday() checks only the holiday date and ignores Holiday.location.
Therefore any holiday date affects working-day calculations for every employee,
including populated location-specific holidays.

The reported selective display bug specifically affects /holidays/my.
Location-specific holiday semantics are not applied by isHoliday(), so this is
an additional existing inconsistency for attendance and other consumers that
use WorkingDaysService.

Sunday/weekend rules and payroll-lock behavior are unrelated to this visibility
bug and should remain unchanged.

G. SMALLEST SAFE FIX
--------------------
Modify only:

  src/holidays/holidays.service.ts

Update employee visibility so NULL, empty, and whitespace-only locations are
treated as global holidays.

This is the smallest safe runtime fix because it:

  - fixes existing database rows already stored as "";
  - fixes future blank or whitespace submissions;
  - preserves populated location-specific behavior;
  - does not change the frontend;
  - does not make Location mandatory;
  - does not require a schema or migration change.

Optionally, create and update paths could normalize blank values to NULL for
future data consistency. That alone would not fix existing empty-string rows,
so the employee filter must still recognize blank values as global unless the
existing data is separately repaired.

Conclusion
----------
The issue is caused by an empty frontend Location being persisted as "" while
the employee filter recognizes only NULL as global. The smallest safe fix is to
make the backend employee visibility predicate treat blank and whitespace-only
locations as global, without changing the UI, schema, migrations, or business
rule for populated locations.
