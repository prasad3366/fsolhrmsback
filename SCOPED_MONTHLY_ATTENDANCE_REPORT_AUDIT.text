1. CURRENT CONCLUSION
---------------------
The proposed feature is feasible without changing the existing database schema.

The safest implementation is a new scoped, paginated Reports endpoint built on
existing Attendance business logic, with a batch calculation path to avoid
per-employee N+1 queries.

The existing system already provides most required business rules through:
- AttendanceService.getEmployeeMonthlySummary()
- WorkingDaysService.getWorkingDates()
- Existing approved-leave calculations
- Existing Reports team authorization
- Dashboard attendance export patterns

2. EXISTING REUSABLE LOGIC
---------------------------

AttendanceService

File: src/attendance/attendance.service.ts

getEmployeeMonthlySummary() already handles:
- Current and historical months.
- Future-month handling.
- Working-day calculations.
- Sales Monday-Saturday behavior.
- Sunday exclusion.
- Holiday exclusion.

WorkingDaysService

AuthorizationService
--------------------
File: src/common/authorization/authorization.service.ts

Existing methods include:
- canAccessEmployee()
- canAccessTeam()
- canAccessOrganizationWide()

Current Reports authorization behavior:
- SUPER_ADMIN, CEO, and HR receive organization-wide scope.
- IT_MANAGER is restricted to authenticated managed teams.
- SALES_MANAGER is restricted to authenticated managed teams.
- Finance is currently denied by ReportsService because no explicit Finance
  Reports scope exists.
- EMPLOYEE, ADMIN, unknown, and unsupported roles are denied.

Scope is derived from authenticated request.user and persisted team relationships.
Client-supplied teamId, employeeId, managerId, and role values are not used for
authorization.

DashboardService

- Working-day calculation.
- Approved leave handling.

It should be used as a reference, not copied as a second attendance engine.

3. REQUIRED REPORT DATA
-----------------------
Each employee row should contain at minimum:
- employeeId
- employee code
- employee name
- department
- team
- working days
- present days
- half days
- absent days
- approved leave days

Summary totals must be calculated by the backend across the complete authorized

Batch calculation recommendation:
1. Resolve authorized employee IDs.

7. Return rows for the requested page only.

called independently for every employee. A shared batch calculation helper may
be needed, but it must not create a second attendance engine.

8. BUSINESS RULES TO PRESERVE
------------------------------
The feature must reuse existing logic for:
- Working days.
- Present days.
- Half days.
- Absent days.
- Approved leave.
- Virtual absences.
- Holidays.
- Sundays.
- Sales Saturday behavior.
- Current-month cutoff.
- Historical months.

Recommended interpretation:
- PRESENT and LATE count as one present day.
- HALF_DAY contributes 0.5 to present-equivalent days.
- Approved leave is counted separately.
- Approved leave is excluded from absent days.
- Missing working-day records become virtual absences where existing Attendance
  logic requires them.

Existing discrepancy to resolve explicitly in tests:
- AttendanceService monthly summary counts only PRESENT as present.
- Existing Reports export counts PRESENT and LATE as present.

The new report must select and document one consistent behavior without changing
existing punch/status rules.

9. DATE AND TIME HANDLING
-------------------------
Recommended internal range:
- date >= localMonthStart
- date < localNextMonthStart

For the current month:
- Cap calculations at the current local business date.
- Do not include future working days.
- Preserve existing local business-date behavior.

Do not use inclusive end-of-day timestamp filtering for the new endpoint.
Do not accept arbitrary timestamp strings for month selection.

Known existing risk:
- The application uses local JavaScript date construction.
- Configured SystemSetting.timeZone is not consistently applied.
- Existing date-only and timestamp parsing can differ across environments.

This feature should preserve existing business-date conventions rather than
introduce a global timezone change.

10. PAGINATION DESIGN
---------------------
Pagination should apply to employees, not attendance records.

Recommended sequence:
1. Resolve authenticated authorization scope.
2. Apply permitted filters.
3. Count matching employees.
4. Fetch one deterministic employee page.
5. Calculate monthly metrics for that page.
6. Return rows and metadata.

Use deterministic ordering such as empCode ASC or employee.id ASC.
Do not load the entire workforce month into the frontend.

11. EXPORT AUDIT
----------------
Existing export options:
- Frontend JSON-to-CSV utility.
- Backend Dashboard CSV export.

Neither directly satisfies the proposed report:
- Existing Reports attendance export lacks monthly workforce metrics and filters.
- Dashboard CSV has stronger attendance rules but cannot populate a paginated
  report table.
- Existing frontend CSV uses a data URI and is not ideal for large exports.

When export is later implemented, it must use the exact same:
- Month/year.
- Department filter.
- Team filter.
- Employee filter.
- Status filter.
- Authorization scope.
- Business calculations.

Export should not use a separate calculation path.

12. DATABASE AND INDEX ASSESSMENT
---------------------------------
No schema change is required for the initial implementation.

Existing relationships are sufficient:
- Employee.userId -> User.id
- AttendanceRecord.userId -> User.id
- Employee.teamId -> Team.id
- Leave.employeeId -> Employee.id

Existing relevant indexes:
- AttendanceRecord unique (userId, date).
- Employee index on teamId.
- Leave index on employeeId.
- Holiday index on date.
- Attendance unique (employeeId, date).

Potential future indexes, only after query-plan verification:
- AttendanceRecord (date, userId)
- Leave (employeeId, startDate, endDate)
- Employee (teamId, status)

Do not add indexes before measuring actual query plans.

13. REGRESSION RISKS
--------------------
1. Calling the current per-employee summary for every row may create N+1 queries.
2. Changing LATE handling may alter existing attendance percentages.
3. Department filtering may include employees outside a manager's teams if it is
   implemented through department alone.
4. Finance behavior is inconsistent across Reports, Attendance, Dashboard, and
   AuthorizationService.
5. Current-month calculations may include future dates if the cutoff is missed.
6. Inclusive end dates may cause month-boundary errors.
7. The repository contains both Attendance and AttendanceRecord models; the new
   report must use AttendanceRecord consistently.
8. Existing tests use local dates and may not expose production timezone issues.
9. Export and table results may diverge if they use separate calculation paths.
10. Summary totals may be incorrectly calculated from only the current page.

17. FINAL RECOMMENDATION
------------------------
The feature can be implemented without changing the existing database schema.

The smallest safe design is a new backend monthly report endpoint with:
- Authenticated scope resolution.
- Server-side employee pagination.
- Existing Attendance, WorkingDaysService, and Leave rules.
- Exclusive month boundaries.
- A typed response.
- One shared calculation path for table data and future export.
