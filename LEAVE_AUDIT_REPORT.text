B. CURRENT END-TO-END FLOW
--------------------------

Apply leave:
Frontend LeaveManagement -> useLeave.applyLeave -> api.applyLeave ->
POST /leaves/apply -> JwtAuthGuard -> authenticated req.user.employeeId ->
AuthorizationService.canAccessEmployee -> LeaveService.applyLeave -> Prisma serializable
transaction -> employee, leave type, policy, overlap, working dates, balance -> Leave PENDING.

Approve:
Frontend approval modal -> useLeave.approveLeave -> api.approveLeave ->
PATCH /leaves/approve/:id -> JwtAuthGuard -> controller management access ->
LeaveService.approveLeave -> authenticated approver Employee -> organization/team check ->
serializable transaction -> conditional PENDING to APPROVED -> balance used increment -> response.

Reject:
Frontend rejection modal -> useLeave.rejectLeave -> api.rejectLeave ->
PATCH /leaves/reject/:id with { remarks } -> JwtAuthGuard -> controller management access ->
LeaveService.rejectLeave -> approver/team check -> Leave status REJECTED -> response.
Rejection is not transactional and does not require the current status to be PENDING.

History:
GET /leaves/history?page=&limit=
- EMPLOYEE: own records only.
- IT_MANAGER/SALES_MANAGER: all records are loaded, then filtered in memory by managed team.
- SUPER_ADMIN/CEO/HR: organization-wide records.
- FINANCE_MANAGER: controller authorization denies Leave history access.

Pending:
GET /leaves/pending
- EMPLOYEE denied.
- Organization roles receive all PENDING records.
- IT_MANAGER/SALES_MANAGER receive managed-team records.

All:
GET /leaves/all
- EMPLOYEE denied.
- Organization roles receive all statuses.
- IT_MANAGER/SALES_MANAGER receive managed-team records.

Balance:
GET /leaves/balance?yearStart=
- EMPLOYEE can read own balance.
- Organization-wide roles can read balances for all employees.
- Managers and FINANCE_MANAGER are denied by Leave controller authorization.

Self history:
GET /leaves/self/history
Uses authenticated employee identity and returns that employee's records.

Self balance:
GET /leaves/self/balance?yearStart=
Uses authenticated employee identity, creates missing balances, then returns balances.

Carry-forward:
POST /leaves/carry-forward with { leaveTypeId, yearStart }
Uses authenticated employee identity and directly updates the current balance row.
There is no pending carry-forward approval state.

Cancellation:
No Leave cancellation endpoint or service method exists.

C. CURRENT BUSINESS RULES
-------------------------

Leave types are stored in LeaveType with yearlyQuota, carryForward, maxCarryLimit,
monthlyAccrual, and requiresMedical. There is no backend LeaveType listing endpoint.
The frontend hardcodes leave type IDs 1, 2, and 3.

CreateLeaveDto accepts:
- leaveTypeId
- startDate
- endDate
- durationType
- reason
- medicalCertificate
- isEmergency

Reason must be non-empty and no longer than 500 characters.
Dates must parse and startDate must not be after endDate.

Duration values are FULL_DAY, HALF_DAY_FIRST, and HALF_DAY_SECOND.
Half-day requires a single eligible working date and stores totalDays = 0.5.
Full-day leave stores the number of eligible working dates.

Leave applications are rejected when overlapping records exist, except REJECTED records.
PENDING, APPROVED, and CANCELLED records block overlaps.
Adjacent ranges do not overlap.

Pending requests do not consume balance. Approval increments LeaveBalance.used.
Rejection does not consume or restore balance.
There is no approved-leave cancellation or restoration path.

Medical certificates are required when the applicable policy/type requires them and totalDays
is greater than two. The certificate content is stored as a string, normally frontend base64.

Rejection remarks are required by the backend, although the frontend labels them optional.

There is no implemented search or filtering for Leave history beyond pagination.
There is no implemented Leave cancellation.
There is no partial-day time-of-day model beyond the first/second half enum.

E. WORKING-DAY AND CALENDAR BEHAVIOR
------------------------------------

The shared WorkingDaysService is used by Leave, Attendance, Payroll, Dashboard, and WFH.

Normal employees: Monday-Friday.
Sales team employees: Monday-Saturday, when team.name exactly uppercases to SALES.
Sunday: always excluded.
Normal Saturday: excluded.
Holiday: excluded.

Holiday matching is date-based and does not filter by employee location.
AttendancePolicy.workDays is not consulted.
Employee location is not consulted.
Employee joining date is not consulted.
Employee exit date is not consulted.
Employee active/inactive status is not consulted for Leave calculation.

Leave calculation strips time through local calendar iteration, while dates are stored as
DateTime values. Payroll also uses raw millisecond/calendar-span calculations. Datetime
offsets and timezone boundaries can therefore produce inconsistent results.

The monthly attendance summary numerically follows:
Working Days = Present + Half Days + Absent + Leave.
Approved leave dates are removed from present/half-day/absent classification and reported
separately. presentEquivalentDays weights attendance half-days by 0.5.

F. BALANCE LIFECYCLE
--------------------

Balance initialization has multiple paths:

1. April scheduler creates all employee/leave-type rows using LeaveType.yearlyQuota.
2. Self-balance creates missing rows using LeavePolicy.annualAllocation when available.
3. Application creates missing rows using policy allocation or LeaveType.yearlyQuota.

Balance consumption happens only at approval.
Approval increments used by leave.totalDays.
Loss-of-pay approval is allowed when policy enables loss-of-pay.

Rejected requests do not restore anything because pending requests did not consume balance.
No approved cancellation restoration exists.

Automatic March carry-forward is commented out. Employee carry-forward directly updates
carryForward on the existing balance. The operation is not transactional.

Pending requests can collectively exceed available balance because they do not reserve days.
There are no database checks preventing negative or inconsistent balance values.

G. ATTENDANCE, PAYROLL, HOLIDAY, AND OTHER INTEGRATION
-------------------------------------------------------

Attendance:
- Only APPROVED leave affects attendance summaries.
- PENDING and REJECTED leave have no attendance effect.
- Approved leave dates are excluded from inferred absences.
- Approved leave dates are excluded from present/half-day/absent classification.
- No persisted virtual attendance row is generated for Leave.

Payroll:
- Only APPROVED leave is included.
- payableDays = presentDays + approvedLeaveDays.
- lopDays = max(workingDays - payableDays, 0).
- Month-spanning leave is prorated using raw calendar span.
- Payroll may disagree with the Leave service's working-day-aware totalDays.

Dashboard and reports query approved leave and reconstruct leave days independently.
Payroll, Attendance, Dashboard, and Reports do not use identical prorating logic.

Employee directory marks employees ON_LEAVE when approved leave overlaps today.
It does not require the employee to be active.

Employee 360 endpoint:
GET /employees/:id/360/leave
Returns employee status, current approved leave, balance summary, leave counts, and five
recent records. The route lists FINANCE_MANAGER, but the service denies FINANCE_MANAGER.

No Leave-specific notification or email workflow was found.

H. API CONTRACT AUDIT
---------------------

POST /leaves/apply
Auth: JWT plus employee profile and employee authorization.
Body: CreateLeaveDto.
Response: Created Leave record.
Errors: invalid reason/date/type/duration, overlap, insufficient balance, medical requirement.

PATCH /leaves/approve/:id
Auth: JWT plus SUPER_ADMIN, CEO, HR, IT_MANAGER, or SALES_MANAGER management access.
Body: none.
Response: approved Leave including employee and leaveType.
Errors: not found, already processed, unauthorized, missing balance, insufficient balance,
serialization conflict.

PATCH /leaves/reject/:id
Auth: JWT plus same management access.
Body: { remarks: string }.
Response: rejected Leave including employee and leaveType.
Errors: missing/long remarks, not found, unauthorized.
Current implementation can reject statuses other than PENDING.

GET /leaves/history?page=&limit=
Auth: JWT. Role-dependent scope.
Response for paginated paths:
{ data: Leave[], pagination: { page, limit, total, totalPages } }.

GET /leaves/pending
Auth: JWT plus management access.
Response: Leave[] with status PENDING.

GET /leaves/all
Auth: JWT plus management access.
Response: Leave[] with all statuses.

GET /leaves/balance?yearStart=
Auth: employee self or organization-wide Leave roles.
Response entries contain employeeId, employeeName, leaveType, allocated, used,
carryForward, remaining.

GET /leaves/self/history
Auth: JWT and employee profile.
Response: Leave[].

GET /leaves/self/balance?yearStart=
Auth: JWT and employee profile.
Response entries contain leaveType, allocated, used, carryForward, remaining.
The response does not contain leaveTypeId.

POST /leaves/carry-forward
Auth: JWT and employee profile.
Body: { leaveTypeId, yearStart }.
Response: { message }.
Current endpoint directly changes carryForward.

Frontend/backend mismatches:
- Frontend calls /leaves/self/monthly, but backend has no matching route.
- Frontend expects self-balance leave type IDs, but backend omits them.
- Frontend sends medicalCertificateFileName, but backend does not persist it.
- Frontend allows a HALF_DAY type in TypeScript, while backend accepts only the two enum values.
- Frontend rejection text says remarks optional, backend requires remarks.
